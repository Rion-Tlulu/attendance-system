## 対象と判定

次の原本を読み、現在のソース、テンプレート、CSS、テスト、Chrome表示と照合した。

- `勤怠管理システム_要件定義書_最小構成版_v1.5.6.docx`（本文21章、F01〜F13、T01〜T19）
- `勤怠管理_v1.5.6_ケース01_全13画面デザイン.pdf`（7ページ、共通・社員・管理の13画面）

確認対象はコミット `1295798` を基点とする今回の作業ツリー。以前の `v1.5.6-acceptance-report.md` にあるPostgreSQL・負荷・復元試験の実績は、今回実施した試験とは区別する。

F01〜F13の主要機能と13画面は実装され、共通CSSおよび画面別CSSが適用されている。照合で判明した機能・操作上の不足は下記のとおり修正した。今回の確認は画面の構造、配色、カード、表、フォーム、狭幅での操作を対象とし、PDFとのピクセル単位の一致を保証するものではない。PostgreSQLの並行試験、実機の支援技術評価、本番運用の確認が残るため、T01〜T19の全条件合格・リリース可とは判定しない。

## 発見した不足と修正

| 不足 | 修正内容 |
| --- | --- |
| 雇用情報画面で部署を自由入力でき、自動採番・番号履歴の経路を迂回できた | 部署を参照専用にし、改変したPOSTも拒否。部署異動はA03の登録済み部署選択へ誘導する。 |
| 在籍日更新中に実行者の権限が失われても、保存時に確認していなかった | 同一トランザクション内で実行者をロックして再確認する。在籍日は社員情報側にも同期する。 |
| E03確認画面から入力へ戻ると修正案・理由が失われた | 署名と期限・本人・nonceを検証したPOSTで日時・複数休憩・理由を復元する。確認画面には修正前の有効値も表示する。 |
| A03/A07確認画面の戻る操作がインラインJavaScriptに依存し、本番CSP下で入力を保持できなかった | JavaScriptに依存しないPOSTに変更。入力値と操作IDを保持し、戻る操作では社員・部署・番号を登録しない。 |
| 通知の未読絞込みが最新20件の中だけを対象にしていた | サーバーで未読を絞り込んでから20件取得する。読込失敗・再試行と空状態を区別する。 |
| 通知モーダルの背景が操作可能で、既読と対応状態も同時に確認できなかった | 背景をinertにし、スクロールを抑止。終了後に元の状態と起点フォーカスを復元する。既読と業務状態は別々に表示する。 |
| 狭幅で通知が空の小さなボタンになり、ヘッダーから階層メニューを開けなかった | 通知とアカウントの文字ラベルを維持。44pxの操作領域を確保し、ヘッダーメニューと開閉状態・Esc後の起点復帰を追加する。 |
| A02/A06の一覧がスマートフォンでも横長の表だった | 全項目を保持したラベル付きカード表示へ切り替える。 |
| A06に対象社員の検索がなかった | 社員番号・氏名、利用状態、管理権限の検索と25人単位のページ切替を追加。全体の有効管理者数は検索で変えない。 |
| A02/A03/A05/A06の詳細から戻ると検索条件やページを失った | 画面別に許可した検索項目とページをセッションに保持する。同一画面を別タブで検索した場合は最後の検索を戻り先に使う。 |
| A02審査の入力エラーで差戻し理由を失った | 同じ詳細画面に理由と項目エラーを表示する。 |
| A05検索で2月31日などを指定すると例外になった | 日付パーサーの例外を入力エラーとして扱い、条件を保持した画面で案内する。 |
| Font Awesomeが不要なスタイルを含めて読み込まれ、SRIがなかった | 7.3.1のコア・Solid・Regularに限定し、配信内容から検証したSHA-384 SRIを固定する。 |
| 運用手順に旧版のCSV取込手順・通知削除時刻・負荷人数が残っていた | v1.5.6の受渡し範囲、毎日09:00、登録100人・同時20人の基準に修正する。外部素材と静的ファイルの配信手順も記録する。 |

## 今回の検証結果

- Djangoテスト: **304件中293件成功、PostgreSQL専用11件スキップ**。追加した9件は通知の未読範囲、確認画面の入力保持、部署変更の迂回防止、保存時の権限再確認、検索の復元・管理者人数表示、審査エラー時の入力保持を確認する。
- SQLiteの隔離テストDBを使用した。テスト実行だけパスワードハッシャーをMD5へ差し替えて処理を短縮しており、アプリ設定・実データのパスワードは変更していない。
- `manage.py check`: 問題なし。`makemigrations --check --dry-run`: モデル変更なし。`git diff --check`: 問題なし。
- Chrome: 13画面と追加状態の計17ルートを、320・375・768・1280 CSS pxで確認（**68ケース**）。本番と同じCSPを適用し、外部フォント・CDNを遮断した。全ケースでHTTP 200、ローカルCSSの適用、JavaScript実行エラーなし、ローカル静的ファイルの404なし、ページ全体の横はみ出しなし。
- E02/A01/A04のグラフは4幅ずつ計12ケースで描画できた。表の領域内に必要な横スクロールは、ページ全体のはみ出しと区別している。
- 通知の背景inert、閉じた後の解除とフォーカス復帰を4幅で確認。320pxではヘッダーメニューの開閉・Esc・起点復帰も確認した。
- 本番CSP下のChromeで、社員登録・部署登録・修正申請の確認画面からの入力保持、通知の取得失敗からの再試行成功を確認した（`interactions.json`）。
- Font Awesomeの3つの固定CSS URLはHTTP 200で取得し、SHA-384を計算してテンプレートへ反映した。
- 外部通信を許可したChromeでもFont Awesomeのフォント読込みに成功し、SRI・CSPを含めコンソールエラーはなかった（`online-A06-1280.png`）。

ローカル証跡は `.local/review/` に保存している。`browser-results.json` が68ケース、`tests-complete.log` が全テスト、画面ID・幅付きPNGがスクリーンショット。検証用DBとライブラリも同ディレクトリー以下に分離した。既存の実DB・利用者のアカウント・添付原本は変更していない。
